# The LLM & Post-Extraction Systems Map

**Read this first.** Every LLM-driven and post-extraction processing system in the backend, grouped by lifecycle stage. Born from the AttributeOntologyService incident (a whole LLM service went undiscovered for weeks because nobody had a census). Regenerate with the greps in the last section.

**The one-gateway law:** every LLM call goes through `LLMService` (`apps/api/src/modules/external-integrations/llm/llm.service.ts`). Every `.md` file in `.../llm/prompts/` is a system's rule text. Every judge lane writes `claim_verdicts` (verdict-first, effect-second, `executedAt` last — `claim-verdict-ledger.service.ts`).

**claim_verdicts lanes (complete):** `entity_match` · `entity_dedupe` · `restaurant_name` · `word_claim` · `word-genericness` · `word-negation` · `word-role` · `concept_satisfies` · `attribute_merge` · `place_grounding` — plus one ORPHAN: `dish.knowledge_synthesize`, hardcoded as a bare string in `dish-knowledge-synthesis.service.ts` with no `*_LANE` constant or adapter (lane-enumeration tools miss it). Note naming drift: the three word-vocabulary lanes use hyphens, everything else underscores. The relevance gate does NOT use this ledger — it has its own verdict table, `collection_relevance_verdicts` (keyed by prompt hash).

## Responsibility overlaps (flagged, not judged)

1. **Two vocabulary-learning lanes from unmet search demand:** demand-vocabulary (single words, manual, entity-match prompt) vs unsegmented-residue (multi-token, cron, residue prompt) — different triggers, prompts, no shared budget.
2. **Two dedupe-merge services** (food vs attribute) with parallel plan-in-verdict machinery and different judges (`entity-match` vs `attribute-merge` prompts); user-anchor rehome is shared but the scan/merge shells are twins.
3. **Attribute placement vs attribute dedupe-merge** both unify attribute vocabulary (pending-time placement vs live-pair merging).
4. **Three "is this word real vocabulary" courts:** word-vocabulary facets, word-claim adjudicator, restaurant-name court — deliberately split by claim type, but all sweep `entity_surface`.
5. **Span-grounding logic in two unrelated places:** extraction's observed-span contract vs search query interpretation — no shared contract.
6. **Cuisine knowledge from two directions:** restaurant cuisine extraction (Places summary → cuisines) and dish-knowledge synthesis (dish → cuisine facet) both write cuisine attribution; both route through alias management.
7. **Two 4AM derived builders** (name-containment + sibling edges) collide against the base class's stated staggering intent; 6AM also carries two crons (knowledge maintenance + curated lists) — only the 3AM family was consolidated into a coordinator.
8. **Two verdict stores:** relevance gate's `collection_relevance_verdicts` vs everyone else's `claim_verdicts` — same buy-once/re-buy-on-rule-change idea, two implementations; the gate gets none of the ledger's budget metering, rehearing gates, or crash-resume.
9. **One prompt, two lanes:** `entity-match-prompt.md` backs both `entity_match` (resolution) and `entity_dedupe` (offline merge) — a version bump must be reasoned about for both.
10. **FOUR prompt-fingerprint mechanisms:** the DB prompt registry (2 of ~20 prompts), llm.service's eager readFileSync fleet (unversioned — changes silently on deploy), the hand-maintained `*-rule.ts` release files, and cuisine extraction's own input-fingerprint hash. The registry's comment says "never a parallel loader"; three parallel loaders remain.
11. **Ledgered vs unledgered attribute merges:** ontology placement's `applyPlan` merges without verdicts; the dedupe-merge lane ledgers them — divergence risk if the gated lane activates.
12. **Merge vs satisfies blind spot:** a `satisfies` verdict on a lexically distant pair (soup dumplings / xiao long bao) is a merge signal the trigram-recall dedupe pipeline structurally cannot see.

## How to keep this current

Run from `apps/api/`:

```bash
# Every LLM gateway caller (any new file here = a new system):
grep -rln "llmService\." src --include="*.ts" | grep -v spec | grep -v "llm/"

# Every prompt file (every .md is a system's rule text; find its loader):
ls src/modules/external-integrations/llm/prompts/
grep -rn "<prompt-file-name>" src --include="*.ts" | grep -v spec

# Every verdict lane:
grep -rhn "LANE = '" src --include="*.ts" | grep -v spec

# Every cron:
grep -rn "@Cron(" src --include="*.ts" | grep -v spec

# Every Bull worker:
grep -rln "@Processor" src --include="*.ts" | grep -v spec

# Every derived-table rebuild job:
grep -rn "extends DerivedIndexJob" src --include="*.ts" | grep -v spec

# Every gating flag:
grep -rhon "process\.env\.[A-Z_0-9]*" src --include="*.ts" | sed 's/.*process.env.//' | sort -u
```

If any grep returns a file this document doesn't name, the map is stale — add the system here in its lifecycle stage.
